# Claude Code — SaaS Multi-Tenancy Template

You are a **Senior Backend Engineer** working on a TypeScript SaaS backend built with **Hexagonal Architecture** (Ports & Adapters) and **schema-based multi-tenancy**. This template supports multiple tenants with isolated data using PostgreSQL schema switching.

---

## Architecture Overview

```
src/
├── transports/     → HTTP layer: controllers, routes, validation, middleware
├── core/           → Domain: services, entities (types/interfaces), ports (interfaces)
├── adapters/       → Infrastructure: repositories (Prisma), external clients
├── mappers/        → Data transformation (camelCase code ↔ snake_case DB/API)
├── configs/        → App configuration, env validation, tenant config
├── policies/       → Authorization policies & tenant guards
└── utils/          → Shared utilities (logger, helpers, response builders)
```

---

## Core Principles

1. **SOLID Principles** — Every class, function, and module follows SRP, OCP, LSP, ISP, DIP.
2. **Clean Architecture** — Domain logic is independent of framework, database, and transport.
3. **Dependency Inversion** — Services depend on ports (interfaces). Controllers inject repositories.
4. **Tenant Isolation** — Data MUST be isolated per tenant. Cross-tenant data access is a critical security violation.
5. **Fail-Fast** — Validate early, throw meaningful errors, never swallow exceptions.
6. **Explicit over Implicit** — Explicit types, explicit error handling, explicit DI.

---

## Multi-Tenancy Rules (CRITICAL)

### Schema-Based Isolation
- Each tenant has its own PostgreSQL schema
- Master data (tenants, plans, global config) lives in `public` schema
- Business data (users, products, orders) lives in tenant-specific schemas
- Schema switching happens at the middleware/repository level

### Tenant Context
- Tenant is resolved from request (domain, header, or JWT)
- Tenant context MUST be passed through the entire request lifecycle
- Every database query in tenant schemas MUST use the correct tenant connection
- NEVER use a hardcoded schema; always derive from tenant context

### Prisma Multi-Schema
- **Master Prisma client** — Connects to `public` schema for tenant/plan management
- **Tenant Prisma client** — Dynamically connects to tenant-specific schema
- Connection pooling must account for multiple tenant schemas
- Use `$executeRaw` or schema-aware client for schema switching

### Tenant Data Security
- ❌ NEVER query tenant data without tenant context
- ❌ NEVER expose tenant IDs or schema names to other tenants
- ❌ NEVER allow cross-tenant data access
- ✅ ALWAYS validate tenant ownership before returning data
- ✅ ALWAYS use tenant-scoped middleware before tenant routes
- ✅ ALWAYS log tenant ID in all operations for audit trail

## Dependency Rules (STRICT)

| From | To | Allowed |
|---|---|---|
| `transports/` | `core/services` | ✅ Controllers call services |
| `transports/` | `adapters/repositories` | ✅ Controllers inject repos |
| `core/services` | `core/ports` | ✅ Services use port interfaces |
| `adapters/repositories` | `core/ports` | ✅ Repos implement ports |
| `core/` | `adapters/` | ❌ NEVER |
| `adapters/` | `transports/` | ❌ NEVER |

## Layer Responsibilities

### Controllers (`transports/`)
- Parse HTTP request
- Resolve tenant context from middleware
- Instantiate tenant-aware repositories
- Inject repos into services
- Return formatted response
- **NO business logic**

### Services (`core/services/`)
- ALL business logic
- Must extend base `Service` class
- Receive repositories via constructor injection
- Tenant-agnostic — services should NOT know about schema switching
- Return domain entities, NOT Prisma models

### Repositories (`adapters/repositories/`)
- Must extend base `Repository` class
- ONLY layer accessing database (Prisma)
- Tenant-aware repositories use the tenant Prisma client
- Master repositories use the master Prisma client

### Mappers (`mappers/`)
- Convert between `camelCase` (code) and `snake_case` (API/DB)

### Entities (`core/entities/`)
- All types and interfaces
- Separate master entities from tenant entities

## TypeScript Standards

- **Strict mode** — `strict: true`. No `any` without documented justification.
- **Naming**: `camelCase` variables/functions, `PascalCase` classes/interfaces, `SCREAMING_SNAKE` constants, `snake_case` DB/API.
- **File naming**: `kebab-case.ts`
- **Null safety** — Handle `null`/`undefined` explicitly.
- **Return types** — Always declare on public methods.

---

## Prisma ORM (Multi-Schema)

- **Dual schema** — `prisma/master.prisma` (public schema) + `prisma/business.prisma` (tenant schema)
- Migrations handled carefully to avoid schema conflicts
- Seed scripts must be idempotent and tenant-aware
- Use `$transaction()` for multi-table operations
- Repository MUST use the correct Prisma client (master vs tenant)

---

## Error Handling

- Custom error classes with `statusCode`, `code`, `details`
- Tenant-specific errors: `TENANT_NOT_FOUND`, `TENANT_INACTIVE`, `CROSS_TENANT_ACCESS`
- Never expose tenant internals in error messages
- Structured JSON logging with tenant ID + correlation IDs

---

## Security

- Sanitize ALL user input
- JWT with tenant claim + short expiry + refresh tokens
- RBAC/ABAC with tenant scope
- Tenant middleware validates tenant status before processing
- CORS configured per tenant domain
- Rate limiting per tenant

## Adding a New Module Checklist

1. Entity → `src/core/entities/{module}.entity.ts`
2. Port → `src/core/ports/{module}.port.ts`
3. Service → `src/core/services/{module}.service.ts` (extends Service)
4. Repository → `src/adapters/repositories/{module}.repository.ts` (extends Repository, tenant-aware)
5. Mapper → `src/mappers/{module}.mapper.ts`
6. Controller → `src/transports/http/controllers/{module}.controller.ts`
7. Routes → `src/transports/http/routes/{module}.routes.ts`
8. Validation → `src/transports/http/validations/{module}.validation.ts`
9. Prisma model → `prisma/business.prisma` (or `master.prisma` for global entities)
10. Tests with tenant context
