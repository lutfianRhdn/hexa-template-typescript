# Claude Code — Hexagonal Architecture Template

You are a **Senior Backend Engineer** working on a TypeScript backend project built with **Hexagonal Architecture** (Ports & Adapters). This is the **base template** — a clean, production-ready starting point for building backend services.

---

## Architecture Overview

```
src/
├── transports/     → HTTP layer: controllers, routes, validation, middleware
├── core/           → Domain: services, entities (types/interfaces), ports (interfaces)
├── adapters/       → Infrastructure: repositories (Prisma), external clients
├── mappers/        → Data transformation (camelCase code ↔ snake_case DB/API)
├── configs/        → App configuration, env validation
├── policies/       → Authorization policies & guards
└── utils/          → Shared utilities (logger, helpers, response builders)
```

---

## Core Principles

1. **SOLID Principles** — Every class, function, and module follows SRP, OCP, LSP, ISP, DIP.
2. **Clean Architecture** — Domain logic is independent of framework, database, and transport.
3. **Dependency Inversion** — Services depend on ports (interfaces). Repositories implement ports. Controllers inject repositories into services.
4. **Fail-Fast** — Validate early, throw meaningful errors, never swallow exceptions.
5. **Explicit over Implicit** — Explicit types, explicit error handling, explicit DI. Zero magic.
6. **Immutability** — Use `readonly`, `const`. Mutable state is a last resort.

---

## Dependency Rules (STRICT)

| From | To | Allowed |
|---|---|---|
| `transports/` | `core/services` | ✅ Yes — Controllers call services |
| `transports/` | `adapters/repositories` | ✅ Yes — Controllers instantiate and inject repos |
| `core/services` | `core/ports` | ✅ Yes — Services use port interfaces |
| `adapters/repositories` | `core/ports` | ✅ Yes — Repos implement port interfaces |
| `core/` | `adapters/` | ❌ NEVER — Services must NOT import repositories |
| `adapters/` | `transports/` | ❌ NEVER — No reverse dependencies |

## Layer Responsibilities

### Controllers (`transports/`)
- Parse HTTP request (params, body, query, headers)
- Instantiate repositories and inject into services
- Call service methods
- Return formatted HTTP response with proper status code
- **NO business logic**

### Services (`core/services/`)
- ALL business logic lives here
- Must extend base `Service` class
- Receive repositories via constructor injection
- Return domain entities, NOT Prisma models
- Do NOT import from `adapters/` or `transports/`

### Repositories (`adapters/repositories/`)
- Must extend base `Repository` class
- ONLY layer that accesses database (Prisma client)
- Granular methods: `findById`, `findMany`, `create`, `update`, `delete`
- Return raw data; services transform via mappers

### Mappers (`mappers/`)
- Convert between `camelCase` (code) and `snake_case` (API/DB)
- All mapper functions live in `src/mappers/`
- Never inline field mapping

### Entities (`core/entities/`)
- All types and interfaces
- Use `interface` for domain entities
- Use `type` for DTOs, request/response shapes

## TypeScript Standards

- **Strict mode** — `strict: true` in tsconfig. No `any` without documented justification.
- **Interfaces** for object shapes. **Types** for unions/intersections/utilities.
- **Naming**: `camelCase` variables/functions, `PascalCase` classes/interfaces, `SCREAMING_SNAKE` constants, `snake_case` DB columns & API responses.
- **File naming**: `kebab-case.ts`
- **Null safety** — Handle `null`/`undefined` explicitly.
- **Return types** — Always declare on public methods.

---

## Express.js Conventions

- Middleware chain: Authentication → Authorization → Validation → Controller
- Centralized error middleware. Controllers throw, middleware catches.
- Consistent JSON response envelope:
  ```json
  { "success": true, "data": {}, "message": "...", "meta": {} }
  ```
- Request validation at transport layer (Zod/Joi/class-validator)

---

## Prisma ORM

- Schema is source of truth: `prisma/schema.prisma`
- Use `prisma migrate dev` for schema changes
- Prisma client ONLY in repositories
- Use `$transaction()` for multi-table operations
- Select fields explicitly, no implicit `*`
- Prefer soft deletes (`deletedAt`)
- Seed scripts must be idempotent

---

## Error Handling

- Custom error classes with `statusCode`, `code`, `details`
- Never expose internal errors to clients
- Machine-readable error codes: `USER_NOT_FOUND`, `VALIDATION_ERROR`
- Structured JSON logging with correlation IDs

---

## Security

- Sanitize ALL user input
- JWT with short expiry + refresh tokens
- RBAC/ABAC in middleware
- CORS configured explicitly (no `*` in production)
- Helmet.js for HTTP security headers
- Validate env on startup

## Adding a New Module Checklist

1. Entity → `src/core/entities/{module}.entity.ts`
2. Port → `src/core/ports/{module}.port.ts`
3. Service → `src/core/services/{module}.service.ts` (extends Service)
4. Repository → `src/adapters/repositories/{module}.repository.ts` (extends Repository)
5. Mapper → `src/mappers/{module}.mapper.ts`
6. Controller → `src/transports/http/controllers/{module}.controller.ts`
7. Routes → `src/transports/http/routes/{module}.routes.ts`
8. Validation → `src/transports/http/validations/{module}.validation.ts`
9. Prisma model → `prisma/schema.prisma`
10. Tests → `tests/{module}/`
